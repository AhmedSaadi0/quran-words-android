The short story

One anonymous user, one phone, one 118 MB offline database. The app has strong bones — feature folders, typed navigation, ViewModels, contracts — but several user-visible bugs and a handful of architectural shortcuts grew inside those bones.

01 What the app is

A reference utility: read the mushaf by surah or real printed page, tap any word for morphology, follow its root to classical meanings and every Quran occurrence, search across five scopes, and keep bookmarks — all offline after a one-time database download.

02 What the audit found

Search results showed a fake verse marker ﴿٠﴾; "Bookmark selection" could delete existing bookmarks; some Retry buttons did nothing; failures were swallowed into blank text or endless spinners. Underneath: one UI file imported the data layer directly, state lived in five different places, and two copies of the mushaf text builder had to be kept in sync by hand.

03 What this plan does

Fixes the user-visible bugs first with one test each. Then closes the architecture boundary, consolidates state, splits oversized files without changing behaviour, cleans up localization and accessibility, and finishes with focused tests. Each phase is safe to stop after.

Why these changes are good for this project

This is not a rewrite for style. Every item protects something the product promises.

Correct Quran data

Removing the fake ﴿٠﴾ marker and making verse references exact protects the one thing a reference app cannot get wrong: the ayah the user is looking at.

User data is safe

Bookmarks are the only data the user creates. Turning "Bookmark" into a real add (instead of a toggle) in one atomic write stops the app from silently removing them.

Failures become recoverable

A 118 MB download and a GitHub manifest can fail. Typed errors plus visible Retry states replace spinners and "database missing" messages that were simply wrong.

Arabic readers come first

Localized TalkBack labels, Eastern digits, 48dp touch targets, and vector icons instead of emoji directly serve elderly and low-vision readers — the audience the product was designed for.

Changes stop rippling

Six God files held seven unrelated jobs. Splitting them by responsibility means a reader gesture fix no longer risks the setup screen, and a copy/share change no longer touches database code.

Tests can finally catch regressions

Today there is one Compose screenshot test. Adding a focused test per fixed bug turns "we think it works" into "this exact failure cannot come back unnoticed".

Before / after, in one glance

Before · error handling

An exception is caught and turned into an empty list or a blank string. The screen shows a spinner, a false "DB missing" message, or "nothing to copy". Nobody can tell what failed.

After · error handling

The failure becomes a typed Result.Error, flows into UiState.error, and renders a message with Retry. A real failure is never confused with an empty result.

Before · architecture

The setup ViewModel imports data.remote classes. UI tests need the real download implementation, and a data-layer rename forces a UI rewrite.

After · architecture

A domain port sits between them. The UI knows an interface and domain models; the data layer implements it. Fakes make tests cheap.

Before · state

Screens hold popup, font-sheet and page-jump state; one screen even reads system settings and drives the Android status bar. State is duplicated across parallel flows with positional casts.

After · state

One typed UiState per feature, events and one-shot effects, and a Route that owns the platform boundary. Screens become previewable and testable.

Before · duplication

Two mushaf text builders with a "keep in sync" comment, two file-size formatters, two clipboard writes, three paging state machines, five copies of the default font size.

After · duplication

One builder, one pure formatter, one clipboard write, one paging helper, one FontSizePreference.DEFAULT. Drift becomes impossible rather than a review chore.

Decisions & exceptions that need a human answer

The plan does not silently change product behaviour in these four spots.

Decision #37 vs #42

The field isActiveSurah says only the active surah owns selection and TalkBack on a shared page; the pager passes null so every surah is interactive, which matches Decision #42. P1-4 asks the owner to pick one and record it. Recommendation: keep current behaviour, delete the unused field.

DB-missing product rule

AGENTS §8.5 says only the download screen shows when the database is missing; the app currently offers a preview. P1-5 asks for a decision before any route gating changes.

Settings cycle

P2-9 unifies both entry points on one event API. The cycle will be explicitly chosen and tested (including a path back to System) instead of being implied by a stale comment.

Paging3 vs helper

Decision #12 already deferred Paging3. P2-7 removes duplicated manual paging state and delays now; adopting Paging3 remains a separate ADR, not a hidden part of this plan.

Naming note: the build uses Spotless with ktlint 1.5.0, so the real formatting task is spotlessCheck. ktlintCheck does not exist in this build, even though AGENTS mentions it; the verification checklist uses the actual task.

Phase 0 manual checks — Arabic RTL and English LTR, light and dark

  • ☐ Search any word: the ayah result shows its real number, never ﴿٠﴾.
  • ☐ Select bookmarked and unbookmarked ayat together, press Bookmark: all end up bookmarked; nothing is removed.
  • ☐ Force a paging failure: WordAyat and Search keep results and their Retry loads the next page.
  • ☐ Force a reader database failure: an explicit error and Retry appear, not a spinner or a false "DB missing".
  • ☐ Force a Play update failure: a failure banner appears and can be dismissed.
  • ☐ Long-press a word, tap outside: only the toolbar closes; the top bar stays as it was.
  • ☐ Pages mode: swipe to an uncached page; Continue Reading on Home updates to that page.
  • ☐ Open legacy unpaged data: no crash, no page header or separator.
  • ☐ Open the report link with no browser installed: a snackbar explains it.
  • ☐ TalkBack on a search result announces "Bookmark ayah" before saving and "Remove bookmark" after.

Why this order, and what to watch

Safe ordering

  • Phase 0 first so users get correct behaviour before any structural change.
  • Phase 1 before refactors so error paths and boundaries are fixed while code is still familiar.
  • Phase 2 before splits so files are divided along a state model that is already settled.
  • Phase 3 is move-only; screenshots and existing tests must stay identical.
  • Phase 4 after structure; tokens and strings then land in stable homes.

Known risks / limits

  • Two product decisions (active surah, DB gating) need the owner before code changes.
  • New Compose tests need no new dependency, but must be verified on the project's Robolectric setup.
  • Paging3 remains deferred; this plan only removes duplication in the current manual approach.
  • Nothing here has been built or run yet — all findings are static-verified, and device QA is still required.
Definition of done for the whole plan: 55 checkboxes closed, each Phase 0 bug has a failing-if-reverted test, the four Gradle checks above pass with user-provided output, and the manual QA list is clean in both locales.
